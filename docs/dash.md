# dash register and watch

`~/.shlib/dash` is a user-maintained register of symlinks to configuration
files that should be watched for changes. Lion never creates, moves or deletes
these links. It only reads them, stores lock copies and reports drift.

## Layout

```text
~/.shlib/
├── dash/                              # user-maintained symlinks (0700)
│   ├── gitconfig -> ~/.gitconfig
│   └── ssh-config -> ~/.ssh/config
├── locks/
│   ├── gitconfig.lock                 # content copy, mode 0600
│   └── shlib-version-of.zshrc         # unchanged shlib lock
└── shlibs/
    └── 99-lion-watchdog.sh            # managed by watch-dog (0644)
```

Dash entries are direct, non-hidden children of `dash/`. There are no
categories and no recursion. `install` creates `dash/` with mode `0700`; an
existing tree without it is not migrated automatically. Create it manually
until `lion doctor` diagnoses the gap.

## `lion dash list`

```bash
lion dash list
```

```text
dash: ~/.shlib/dash
gitconfig: locked, file -> ~/.gitconfig
ssh: unlocked, dir -> ~/.ssh
broken: unlocked, broken -> ~/missing
notes: unlocked, not-a-link
```

Only metadata is read: `lstat`, `readlink` and `stat`. File contents and lock
contents are never read. Entries are sorted by link name and hidden names are
ignored.

The type is `file` for a symlink to a regular file, `dir` for a directory,
`broken` for a missing target, `other` for any other target type and
`not-a-link` for a regular file, directory or other entry inside `dash/`.
`not-a-link` entries are only shown so nothing disappears silently.

The lock state is the mere existence of `locks/<name>.lock`; the content is not
inspected. An empty register prints `no entries` and exits `0`. A missing or
symlinked `dash/` is an error that points to `lion shlib install` and exits
`2`.

## `lion dash lock <name>`

```bash
lion dash lock gitconfig
```

```text
locked gitconfig: ~/.gitconfig (1234 bytes, sha256:7e9f...)
```

The lock command copies the current target content byte for byte to
`~/.shlib/locks/<name>.lock` with mode `0600`. An existing regular lock file is
always overwritten without a prompt; there is no `--force`. A second run
reports `updated` instead of `locked`.

The name must be a direct, non-hidden child name without `/` or control
characters. The dash entry must be a symlink that resolves to a readable,
regular file. Directories, broken links, special files and regular files
directly in `dash/` are refused. A symlink or directory at the lock path is
refused, as is a missing or symlinked lock directory. Output names the entry,
the resolved target, the byte count and a short SHA-256; contents are never
printed.

## `lion dash unlock <name>`

```bash
lion dash unlock gitconfig
```

Only `locks/<name>.lock` is deleted. The dash link and its target stay
untouched. A missing lock is a no-op with exit `0`, so an orphaned lock can be
cleaned up without a dash entry. A directory at the lock path is an error; a
symlink at the lock path is removed as the lock entry.

## `lion watch`

`lion watch` is a top-level command so more sources can be added later. It
currently reads only the dash register.

```text
dash: gitconfig: changed
--- lock: ~/.shlib/locks/gitconfig.lock
+++ target: ~/.gitconfig
@@ -1,2 +1,2 @@
 [user]
-name = Old
+name = New
```

Only dash entries with an existing `locks/<name>.lock` are compared; unlocked
links are ignored. A lock file must be regular. A symlink at the lock path is
reported as an error and never followed.

A missing `dash/` or `locks/` directory is silent with exit `0`. This matters
after `lion shlib uninstall`: a flattened `.zshrc` can still run `lion watch`,
and it must not complain on every start. A symlinked or unreadable
`dash/`/`locks/` is an error on stderr with exit `2`.

A clean state prints nothing. Otherwise findings are printed in name order:

- `dash: <name>: changed` followed by a unified diff.
- `dash: <name>: binary content differs (sha256 lock=<short> target=<short>)`
  when either side contains a NUL byte or is not valid UTF-8.
- `dash: <name>: broken link: <target>`
- `dash: <name>: target is missing: <target>`
- `dash: <name>: target is not a regular file: <target>`
- `dash: <name>: not a symlink`
- `dash: <name>: cannot read lock/target: <reason>`

Drift is a normal result and exits `0`. Read and scan errors are reported, the
remaining entries are still checked, and the overall exit code is `2`. There
is no color, no pager and no external `diff`; `difflib` is enough.

## `lion watch-dog on|off|status`

```bash
lion watch-dog on
lion watch-dog status
lion watch-dog off
```

The watchdog is the managed file `~/.shlib/shlibs/99-lion-watchdog.sh` with
mode `0644` and this exact content:

```zsh
# Generated by `lion watch-dog`; do not edit.
command -v lion >/dev/null 2>&1 && lion watch
```

- `on` writes the file atomically and replaces any existing entry.
- `off` deletes the complete file; a missing file is a no-op with exit `0`.
- `status` prints `watchdog: on` for a regular file or symlink and exits `0`,
  or `watchdog: off` for a missing path and exits `1`.

`shlibs/` must be a real directory. If it is missing, `on` fails with a hint
to run `lion shlib install`, `off` is a no-op and `status` reports `off` with
exit `1`. A symlinked `shlibs/` and a directory at the watchdog path are
errors with exit `2`.

There is no protection against manual edits: `on` overwrites and `off` removes
the whole file. That is deliberate.

## Uninstall

`lion shlib uninstall` does not know about dash specifically. The complete
`~/.shlib` tree, including `dash/` and dash locks, moves into
`~/.shlib.uninstalled-<timestamp>/`. `99-lion-watchdog.sh` is flattened into
the new `~/.zshrc` like every other shlib file, so a following `lion watch`
runs without a dash directory and stays silent.

## Limits and safety

- Dash links belong to you. Lion never creates, retargets or deletes them.
- Locks are content copies with mode `0600`; the lock directory is `0700`.
  They can contain secrets.
- `lion watch` prints file contents to the terminal, including secrets. Output
  masking is not part of this change.
- Locks carry no target metadata. Retargeting a link to a different file with
  identical content stays invisible.
- Directory targets are not watched recursively; there are no directory locks.
- Orphaned locks, a missing `dash/` directory in an existing tree and name
  conflicts are doctor cases, not part of `dash` or `watch`.
- There is no locking between concurrent invocations; a single interactive
  user is assumed.
- The new commands have no `--dry-run`, `--force` or `--no-color`; `--home` is
  available everywhere.

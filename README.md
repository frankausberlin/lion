# LION — The Linux Assistant

*(🚧 WIP)* The project is in an early stage of development.


**LION (Linux Operator Nerd)** is your Linux assistant. It tracks the machine status with collectors, enables structured system individualization with the shell library (shlib), optimizes agentic work on the system with an MCP server, enables the storage and management of shell recordings, offers a monitoring mechanism for commands with declarative qualification rules and creates an OKF v0.2 compliant wiki about the system.

***Lion requires no root and modifies no system files. Its writes are confined to Lion's own directories and the shell startup files it manages.***

## Base mechanics

* It's a **command**: `lion [command [subcommand]] [parameter]`
* The **scan creates** a current **system status** with its **collectors** and adds it to the **history**.
* **Status** shows a **summary of the current** status and the **difference from the previous** one.
* The **Shlib system** monitors changes to the **.zshrc** and **organizes** its contents into individual files.
* The **Watch** mechanism records shell input blocks persistently: a recording survives shell restarts and system reboots, while active the prompt carries one red dot, and `#-LION:` / `#+LION:` / `#.LION:` annotation lines attach decisions (ADRs) to it; `lion records` reads and edits them, and `lion watch R`/`R-` classify the blocks in-session.
* **Decisions** need not come from a recording: `lion adr` stores **standalone ADRs** (for example switching the default browser) under `$XDG_DATA_HOME/lion/adrs` ([adr reference](docs/reference/adrs.md)).
* The **watch dog** (`lion watch dog on`) asks for confirmation before critical input runs — independently of a recording (guardrail, not a security boundary; see the [guard how-to](docs/how-to/guard-critical-input.md)).
* With **scan**, an **OKF v0.2** (Open Knowledge Format) compliant wiki is generated from the **current state** ([wiki reference](docs/reference/wiki.md)).
* The **Serve** command starts an **MCP server** (stdio) with **tools, resources and prompts** for agent harnesses: a read-only view of the ledger plus two ADR write tools ([MCP reference](docs/reference/mcp.md)).

## Collectors

|Name|Description|
|-|-|
|`host`|Host identity and operating system: hostname, distribution, kernel, architecture.|
|`hardware`|Stable hardware facts: CPU model and cores, total memory, GPUs with vendor, driver and VRAM.|
|`network`|Physical network interfaces with permanent MAC addresses and kernel drivers.|
|`packages`|Installed Debian packages and `apt-mark` manual/auto/held selections.|
|`services`|systemd `*.service` unit-file states.|
|`containers`|Docker or Podman configuration: engine, images, volumes, networks, containers.|
|`tools`|External tools visible on `PATH` (lspci, nvidia-smi, systemctl, docker, podman, zsh, ...).|
|`dash`|Monitors (hash) all files linked in `~/.shlib/dash` that start with `LIONSTATE_` (only links to files).|

## Classifiers

`lion classify` turns the recorded input blocks of a recording into metadata
with declarative JSON rules; `lion watch R` and `lion watch R-` show the same
classification tersely inside an active recording. Several rules may contribute
to one block; there is no first-match-wins. All rules share one bounded parsing
of the shell input, so command text that is merely printed (for example `echo
"sudo nala install"`) is never classified as an execution. A match is metadata
only; it never claims that an action succeeded. The built-in defaults extend
and override per rule id in `$XDG_CONFIG_HOME/lion/classifier.json`, and the
optional `$XDG_CONFIG_HOME/lion/policies.toml` evaluates each command against
declared work rules; the schema, the group catalog, the ERE subset and the
policy format live in [Classifiers](docs/reference/classifiers.md).

|Group|Example triggers|Emitted information|
|-|-|-|
|packages|apt/nala, brew, uv, pip, mamba, pnpm: install, remove, update|manager, action|
|services|systemctl: start, stop, restart, enable/disable; user/system context|unit, action, scope|
|containers|compose calls; removing containers and volumes|engine, action, target|
|shell/config|source, exec zsh, chsh, detectable config writes|target, action|
|downloads/installers|downloads, git clone, curl piped into a shell|source, action|
|interruptions|reboot, shutdown, logout|action|
|checks|version and known status queries as possible verification|subject, intent|

Rule id, schema version and ruleset version are stored with every
classification; invalid rules are reported loudly. `lion watch dog` reuses the
same rule set: every rule with `guard: "confirm"` is compiled into the guard
artifact and confirmed before execution — one source of truth, no second rule
list ([Configuration](docs/reference/config.md#watch-dog)).

## Watch mode

While a recording is active, annotation lines in the recorded shell input
attach metadata to it — currently one **ADR** (architecture decision record)
per recording. The syntax is comment-based:

| Syntax | Meaning |
|-|-|
| `#-LION: adr.<field> <value>` | the annotation belongs to the **previous** block |
| `#+LION: adr.<field> <value>` | the annotation belongs to the **following** block |
| `#.LION: <value>` | continues the most recently referenced field |

A marker counts only as a full comment line outside strings and here-documents.
All annotation lines of a recording fold into one ADR: `adr.<field> <value>`
sets a field, `adr.<field>` without a value deletes it again, and `adr.title`
plus `adr.decision` together make the ADR complete. `lion records` reads the
ADRs and `lion records edit` maintains them. The full grammar, the field
catalog, the parser limits and the `Unresolved:` findings live in
[Records and ADRs](docs/reference/records-and-adrs.md).

Decisions that exist without a recording are stored as **standalone ADRs** with
`lion adr`; the two views share the field catalog, the completeness rule and the
status values (schema, ids, resolution and JSON in
[Standalone ADRs](docs/reference/adrs.md)).

## Watch dog (guard)

`lion watch dog on` arms a guard in your Zsh: the first Enter on a critical
command (recursive `rm`, reboot/shutdown, volume `rm`/`prune`, a download piped
into a shell) executes nothing and shows the matching rule, editing the buffer
cancels, the second Enter runs it. The rules are the classifier's
`guard: "confirm"` rules, compiled into one small artifact
(`~/.local/share/lion/dog/rules.zsh`) — no process in the input path, no
recording required. The guard is a guardrail, not a sandbox; it loads through
the watch integration and applies to new shells.
[Guard critical input](docs/how-to/guard-critical-input.md) walks through it.

## MCP server (serve)

`lion serve` runs an **MCP server on stdio** for agent harnesses: eleven tools,
four resources and three prompts over the stored ledger. It is a read-only view
of the states, recordings, ADRs and classifications — only `lion_adr_add` and
`lion_adr_update` write, and only into the standalone ADR store. No tool ever
collects a state; the ledger changes only through `lion scan` and `lion watch`
on the machine. Text from recordings and ADR fields is masked best-effort
(`LION_SERVE_REDACT=0` opts out).

```json
{
  "mcpServers": {
    "lion": { "command": "lion", "args": ["serve"] }
  }
}
```

The tool catalog, the resource URIs, the prompt defaults and the redaction
rules live in [MCP server](docs/reference/mcp.md); the wiring walkthrough in
[Use LION from an MCP client](docs/how-to/use-lion-from-an-mcp-client.md).

### Examples

These two recordings produce the same ADR:

```shell
lion watch start
sudo apt install some-complex-stuff
#-LION: adr.title complex-stuff-decision
```

```shell
lion watch start
#+LION: adr.title complex-stuff-decision
sudo apt install some-complex-stuff
```

## Quickstart

```bash
git clone https://github.com/frankausberlin/lion.git
cd lion
uv sync
uv run lion scan     # capture the first state
uv run lion status   # compare the current state with the latest stored one
```

See the [getting-started tutorial](docs/tutorials/getting-started.md) for the
guided walkthrough.
